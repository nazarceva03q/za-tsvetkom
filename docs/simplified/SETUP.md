# Упрощённая схема: инструкция будущего запуска

Статус: локальный код, не опубликован. Никакие пункты ниже не выполнены автоматически.
Главная инструкция для нового варианта — этот файл. Инструкции stage1/stage2 описывают предыдущую схему подтверждённых цен и прямой отправки PHP → VK.

## Что где хранится
REG.RU: все заявки сайта, контакты, пожелания, выбранные названия/количество, очередь и защищённая панель Екатерины.
Яндекс: существующие административные диалоги, каталог, фото, служебные сессии бота и отправка уведомления VK.
Браузер никогда не обращается к функции Яндекса для сохранения заявки. Он вызывает только /api/v1/orders.php на своём домене.
Сначала одна транзакция MySQL фиксирует заявку, позиции и очередь. Только затем сайт подтверждает номер.
Сайт на REG.RU может сохранять заявку без Яндекса, catalog.json и фотографий. При недоступном каталоге нельзя гарантировать выбор нового товара, но уже открытая форма обращения и сохранённые заявки от Яндекса не зависят.

## Ещё требуется отдельное разрешение на серверные действия
1. Зафиксировать состояние рабочей базы и сделать свежий экспорт. 001/002 уже применены пользователем — не запускать их снова.
2. Применить только 003-simple-requests.sql, один раз. Она добавляет request_type и разрешает NULL вместо подтверждённой цены. Исторические цены не стираются. После ошибки DDL остановиться и проверить структуру.
3. Обновить private-orders/lib всеми PHP-модулями из backend/orders/lib: Validation, Repository, Http, Notifications, Owner, RequestView, YandexRelay. Новых файлов два. catalog.json можно оставить как старую копию; обработчик его больше не использует.
4. Сохранить реальные DSN/user/password закрытой config.php! Не перезаписывать её config.example.php. Объединить настройки по новому примеру. enabled=false, owner.enabled=false, notifications.enabled=false до проверок.
5. Установить rate_secret и owner.secret разными случайными значениями (32 байта hex), owner.username и owner.password_hash. Пароль Екатерины хранить только хешем. Секреты не отправлять в чат/бот/репозиторий.
6. Настроить ZT_ORDERS_PRIVATE_DIR для FastCGI, размещать публично только api/v1/orders.php, owner/orders.php и owner/orders.css. Скрипты lib, конфигурацию, SQL, архивы и тесты не помещать в www.
7. Сначала проверить защищённый просмотр с owner.enabled=true. Приём заявок можно оставить выключенным. Проверить отсутствие доступа без входа, корректный выход и защитные заголовки. Панель /owner/orders.php работает в браузере телефона и компьютера, логин отдельный от ISPmanager.
8. До открытия форм согласовать legal/consent и сроки хранения. Черновики — legal.proposed.html и consent.proposed.html в этой папке. Автоудаления контактов/заявок не добавлено; процедуру необходимо согласовать. Для версии 2026-10-requests-v2 сайт должен показывать именно утверждённое согласие, а закрытый consent.html — содержать тот же текст и data-consent-version.
9. После утверждения обновить публичные legal.html и consent.html, ссылку формы на consent.html, закрытый consent.html и consent_version='2026-10-requests-v2' в config.php. Корневые документы сейчас не заменены. Черновик нельзя выдавать за опубликованный утверждённый документ. Старый снимок согласия не подходит новому обработчику.
10. Применить согласованную безопасную публикацию вместо старого deploy-reg.yml до выкладки PHP. Сохранить обновления через GitHub; не отключать без разрешения пользователя. Старый workflow не запускать: он может загрузить backend, SQL, тесты и ZIP. Новая структура owner/ и API загружаются отдельно явным списком.
11. Витрина меняется только в app.js, details.js, checkout.js и cache-тегах index.html. checkout-client.js с ключом повторов сохраняется. Товары/фото/цены/категории не менять. Проверить формы корзины, подбора, большого букета, корпоративных подарков, вопроса, предзаказа и остальных обращений.
12. Только после отдельного разрешения включить enabled и отправить свои тестовые данные. Должна появиться одна заявка, её позиции и одна pending-запись. Проверить панель и повторный запрос с тем же ключом. Цена в заявке не подтверждается и не требуется.
13. До включения VK-реле работа магазина возможна через панель: уведомления накапливаются. Екатерина должна регулярно смотреть панель; закрытие вкладки не прекращает сохранение заявок.

## Подключение Яндекса и VK — отдельный этап
Никакие облачные ресурсы сейчас не создавались. Возможные расходы должны быть согласованы заранее.
Существующий каталог/фото в Yandex Object Storage оставляем. Административная схема Node.js не переносится на PHP.

1. Проверить актуальные исходники бота и сохранить текущую конфигурацию/архив. Новый архив: bot/yandex-deploy-simplified.zip. Старые архивы не заменены. Пересборка: из bot/ выполнить node scripts/build-yandex-zip.cjs — только локальное создание ZIP, не деплой. Архив не содержит .env.
2. После разрешения разместить новую версию функции Node.js 22+ с entrypoint index.handler. Настройки каталога и приватного S3 — существующие переменные YC_*. VK_GROUP_TOKEN остаётся только на Яндексе. Сообщество и администраторы настраиваются отдельно, без токенов в переписке.
3. Добавить SITE_RELAY_SECRET: отдельный случайный 64-символьный hex, тот же в закрытой notifications.secret REG.RU. Передаётся только заголовком X-Relay-Key по HTTPS. Для публичной функции это обязательно; она проверяет секрет до любого вызова VK.
4. SITE_BASE_URL — текущий домен магазина. OWNER_ORDERS_URL — его /owner/orders.php. Эта ссылка не содержит логина/пароля/секретов и сама по себе не даёт доступа.
5. notifications.url — точный HTTPS-адрес functions.yandexcloud.net/идентификатор без query; owner_id — тот же персональный VK ID, что VK_OWNER_ID функции. Получатель фиксируется в очереди перед первой попыткой; при несовпадении функция отказывает.
6. Пользовательские сообщения не вызывают автоматический диалог. Админменю и управление каталогом сохраняются. Кнопка заявок открывает панель; старые JSON-заявки не удалены, но больше не являются входящим журналом сайта.
7. После разрешения включить notifications.enabled и выполнить один закрытый запуск bin/notify.php. Проверить сообщение и status=sent. Затем настроить cron: /opt/php/8.3/bin/php /var/www/u3685169/data/private-orders/bin/notify.php. Не создавать публичный cron URL.
8. Cron обрабатывает до пяти заданий за запуск. Lease 120 секунд, HTTP timeout 25 секунд, backoff от минуты до часа. До включения проверить старую очередь — могут отправиться накопленные тестовые обращения.
9. В VK отправляются номер, тип, время, выбранные названия и количество. Имя, телефон, адрес, пожелания и тема обращения туда не передаются. Подтверждённой суммы в этой схеме нет. Полная заявка — только в панели.
10. Приватный S3 хранит квитанцию доставки (хеш/ID сообщения), не копию контактов. При ошибке VK или записи квитанции функция не подтверждает успех; PHP оставляет задачу для повтора. Заказ всё это время доступен в MySQL.
11. Повтор использует сохранённый random_id, текст и получателя. Квитанция позволяет не вызывать VK второй раз после завершённой отправки. При потере квитанции защита зависит от random_id VK: бесконечной гарантии «ровно один раз» нет. После 12 попыток или 12 часов — failed, ручная проверка. Слишком длинное сообщение >4096 символов не обрезается и требует проверки.
12. Failed не пересылать с новым random_id вслепую. Изменение получателя/секрета/функции во время ожидающих заданий требует проверки. Контроль cron и очистка старых квитанций/сессий — отдельная согласованная процедура.

## Каталог
Динамический catalog-sync.js сохраняется. Его публичный catalog-url сейчас пуст; подключение адреса Yandex-каталога/CORS выполняется отдельно после сверки имеющихся 53 товаров и 89 ссылок. Импорт каталога в MySQL не нужен.
В этой задаче не включаем динамический URL и не импортируем статический каталог в пустой бакет. Без этого сайт продолжает показывать существующие файлы каталога.
Фотографии остаются существующими ссылками/файлами; новые административные загрузки используют прежнюю реализацию Яндекса. Автоматического зеркалирования на REG.RU не добавлено.
Сбой Яндекса может временно скрыть облачные фото или остановить обновление каталога; он не удаляет уже сохранённые заявки REG.RU.

## Откат
Выключить enabled и notifications.enabled, сохранить БД и очередь. Вернуть согласованную версию кода, которая честно отказывает в приёме, а не показывает ложный успех.
003 не откатывать удалением строк/таблиц. Исторические суммы сохранены; новая форма несовместима со старым API подтверждённых цен.
Не восстанавливать старую базу поверх поступивших заявок. Экспорт и восстановление — в отдельной тестовой базе.
Если есть неподтверждённая заявка в браузере старой версии, не стирать её ключ без проверки, была ли она сохранена. При запуске на данном проекте прежний API ещё не публиковался, но это нужно перепроверить.
