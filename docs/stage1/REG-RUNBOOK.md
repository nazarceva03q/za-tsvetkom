# REG.RU: безопасный порядок первого запуска

Инструкция для будущих ручных действий ПОСЛЕ отдельного разрешения.
Ни один пункт сейчас не выполнен на хостинге. Не присылайте пароли/токены в чат.

## 0. Что согласовать до любых публикаций

- Завершённую проверку PHP 8.3 + pdo_mysql вместе с MySQL 8.
- Правки проекта workflow, способ отдельной выкладки API и окно публикации.
- Политику, отдельное согласие, сроки/процедуру хранения и удаления.
- Как владелица видит новые заказы до включения cron-уведомлений.
- Резервные копии и откат без восстановления старой базы поверх новых заказов.

Текущий автоматический workflow ещё действует. Нельзя переносить код в main:
сначала отдельное разрешение на замену старого workflow, без второго параллельного.
Даже изменение workflow в main само может запустить публикацию — последовательность
этого изменения необходимо отдельно проконтролировать. После отдельного разрешения
сначала временно отключить старый workflow и проверить отсутствие выполняющихся
и ожидающих старых заданий. Затем заменить его в том же файле ручным вариантом.
Не запускать сохранённые старые задания после выкладки API. Сейчас ничего
из этого не сделано; автоматически ничего не запускаем.

## 1. Найти точные пути и сделать копии

В панели услуги открыть файловый менеджер и настройки сайта/WWW-домена.
Записать фактическую публичную папку WEB_ROOT и домашнюю папку пользователя HOME.
Не считать корень FTP автоматически корнем сайта. Убедиться, что правится именно
цветы-пермь.online. Сохранить копию кода и базы вне публичной папки, проверить
возможность восстановления. Фотографии, uploads и конфигурацию не заменять.

В разделе версий/настроек PHP подтвердить PHP 8.3 FastCGI Apache, pdo_mysql,
закрытый журнал ошибок и display_errors=Off. Проверить, что open_basedir разрешает
PHP читать выбранную закрытую папку. Возможность настройки зависит от тарифа.

## 2. Подготовить базу

Открыть раздел баз данных и phpMyAdmin для нужной базы u3685169_default.
Сначала визуально убедиться в имени базы, версии MySQL и отсутствии четырёх таблиц:
zt_orders, zt_order_items, zt_notification_queue, zt_order_rate_limits.

После разрешения импортировать ТОЛЬКО backend/orders/migrations/001-orders.sql.
В файле нет переноса каталога, удаления или изменения существующих таблиц.
Не применять его повторно вслепую. Если создание оборвалось, остановиться:
DDL MySQL не откатывается как одна обычная транзакция. Осмотреть, что уже создано,
и согласовать дальнейшие действия. Не удалять существующие таблицы «для повтора».

Убедиться, что создано ровно четыре таблицы InnoDB и есть уникальный индекс
idempotency_key. Сохранять реальные заказы в этих таблицах, а не JSON.

## 3. Учётная запись приложения

Предпочтительно отдельный пользователь с минимальными правами на новые таблицы:
SELECT/INSERT для заказов, позиций, очереди; SELECT/INSERT/UPDATE для счётчиков.
Без DROP, ALTER, GRANT и доступа к другим базам. Если панель даёт права только
на всю базу, уточнить у поддержки возможность ограничения либо отдельной базы
для заказов в пределах тарифа. Пользователь миграций не должен быть постоянным
пользователем PHP. Реальные реквизиты вводятся только в закрытом файле.

## 4. Закрытая папка

Через файловый менеджер создать папку вне ВСЕХ публичных каталогов сайтов
пользователя, например HOME/private-orders — только пример, не готовый путь.
В неё скопировать:
- lib/ с тремя PHP-модулями;
- catalog.json — доверенный снимок;
- утверждённый consent.html;
- config.php на основе config.example.php.

SQL, тесты, ZIP, черновики и инструкции в публичную папку не загружать.
Выставить минимальные права, позволяющие PHP читать файлы. Не использовать 777.
Для прав и группы учитывать фактического пользователя FastCGI.

В config.php заполнить DSN из панели, пользователя, пароль, точный HTTPS origin
и случайный rate_secret. enabled пока false. Реальные значения не коммитить,
не отправлять в VK и не помещать в заголовки страницы.

## 5. Публичный шлюз PHP

Отдельно вручную опубликовать ТОЛЬКО api/v1/orders.php по соответствующему пути
в WEB_ROOT. Он не содержит пароля и не создаёт таблицы.

В окружении FastCGI указать ZT_ORDERS_PRIVATE_DIR абсолютным путём к закрытой папке.
Если панель не позволяет это сделать, сначала уточнить поддерживаемый способ
у REG.RU. По отдельному согласованию допустимо указать только абсолютный путь
в шлюзе PHP — без паролей. Не переносить config.php под WEB_ROOT.
При отсутствующей конфигурации API должен честно отказать, а не принять заказ.

## 6. Документы и витрина

Пока подготовлены legal.proposed.html и consent.proposed.html. Они не заменяют
действующие файлы. До выкладки утвердить критерии хранения и удаления, исполнителя
хостинга, доступ и копии. Затем согласованным изменением:
- заменить legal.html утверждённой редакцией;
- добавить отдельный consent.html;
- переключить ссылку согласия формы на этот документ;
- обновить одну и ту же версию в JS, PHP и тестах;
- заменить закрытый снимок согласия и его контрольную сумму.

Каталог и его фотографии при этом не меняются.

Предложенный workflow загружает только явный список файлов витрины.
Первый запуск — dry_run=true; он не подключается к FTP. Реальная выкладка —
только вручную с dry_run=false после проверки корня и резервных копий.
PHP и закрытая папка в этот список не входят. Все фото исключены.

FTPS не даёт атомарного переключения набора JS. Согласовать короткое окно
обслуживания и способ временно закрыть оформление на время замены файлов.
API держать enabled=false, пока все файлы не проверены. Не возвращать старое
ложное подтверждение, даже временно. Проект workflow отправляет index.html последним,
но один этот приём не обеспечивает атомарность.

## 7. Первый согласованный тест

После подготовки и разрешения открыть приём в согласованное окно.
Использовать только свои согласованные тестовые данные с явной пометкой
«ТЕСТ, НЕ ИСПОЛНЯТЬ». Не использовать телефон случайного человека.
Не подключать онлайн-оплату и не обещать резервирование склада.

1. Добавить обычный букет и шары «под заказ».
2. Заполнить контакты, пожелания и доставку.
3. Отправить, дождаться номера.
4. Через закрытую панель проверить одну строку заказа, нужные позиции,
   правильные названия/цены/количества, одну pending-запись очереди и согласие.
5. Проверить повтор того же запроса с прежним ключом: тот же номер, без дублей.
   Это техническая проверка, её лучше выполнить подготовленным тестом.
6. С согласованным выключением enabled=false проверить: нет успеха,
   поля и корзина остаются. После восстановления повтор не должен дублировать заказ.
7. Контролируемые ошибки MySQL, обрыв сети и конкурентные запросы сначала проверять
   только в изолированной среде; не ломать рабочую базу ради теста.
8. Согласовать дальнейшую судьбу тестовых записей. Не выполнять массовую очистку.

Уведомления пока не отправляются: pending — нормальный результат первого этапа.
До отдельного подключения cron владелица должна регулярно просматривать заявки
согласованным защищённым способом. Для постоянной работы нужен удобный закрытый экран.

## 8. Откат и наблюдение

При проблеме enabled=false; пользователю — честная ошибка и телефон магазина.
Вернуть проверенные файлы кода из копии, сохранив безопасную обработку формы.
Не возвращать старый completeCartOrder со списанием браузерного остатка и ложным
успехом. Не выполнять DROP/down-миграцию и не восстанавливать старую БД целиком:
новые заказы, ключи повторов и очередь сохраняются.

Проверять новые заявки, ошибки и очередь. Очистка старых счётчиков/данных —
отдельная согласованная процедура, не часть отката.
