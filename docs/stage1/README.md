## Как сохраняется заявка

1. Сайт отправляет JSON на /api/v1/orders.php своего домена. Секрета в JS нет.
2. Сервер проверяет метод, размер, источник, поля, согласие и позиции.
3. Цена и название берутся из ЗАКРЫТОГО снимка файлов каталога. Цена браузера
   нужна только для обнаружения расхождения; сервер её не принимает на веру.
4. В одной транзакции InnoDB записываются заявка, позиции и pending-уведомление.
   В той же транзакции учитывается лимит новых обращений.
5. Только после COMMIT API возвращает saved:true и случайный номер.
6. Сайт показывает номер и убирает только отправленные количества из корзины.
   Ошибка, не-JSON, 503 или потеря ответа не означают успех и не очищают корзину.
7. Повтор использует прежний ключ; уникальный индекс не допускает второй заказ.
   Если содержание ключа изменилось, сервер отклоняет запрос.
8. Даже при изменении каталога или наступлении следующего дня сохранённый повтор
   возвращает первоначальный номер. История содержит снимок названия и цены.

Остатки из файлов сейчас null: это «подтвердит флорист», а не ноль.
Вымышленное списание localStorage больше не используется. Настоящего складского
резервирования до следующих этапов нет. «Под заказ», в том числе шары, принимаются.

Обычные формы консультации сохраняются как kind=inquiry, с нулём позиций;
их отправка не очищает корзину.

Очередь только записывается. Отправщика VK и cron нет — это следующий этап.
VK/Yandex не вызываются. Административного API и переноса каталога нет.
На первом этапе нужно отдельно согласовать, кто и как просматривает сохранённые
заказы вручную. Нельзя обещать владельцу автоматические уведомления.

Снимок каталога нужно держать согласованным с витриной. Если позднее включить
Object Storage catalog-sync, новые ID/цены без обновления доверенного источника
будут отвергнуты. На этом этапе meta catalog-url остаётся как было: пустым.
Никакого автоматического доверия публичному JSON Yandex не добавлено.

## Повторная отправка

Браузер хранит только ключ, отпечаток запроса, ID/количества и подтверждённый
номер, без имени/телефона/адреса. При неопределённом результате клиент не создаёт
новую заявку с другими данными молча. Нужно повторить прежние данные или
уточнить результат у магазина. Не очищать данные браузера до выяснения.
Автоматических повторов фоновой отправки и офлайн-заказов нет.

При отказе localStorage запрос не начинается: без устойчивого ключа нельзя
обещать безопасный повтор после перезагрузки. Корзина текущей страницы остаётся.
Защита от повторов относится к повтору одного запроса, а не к запрету человеку
сделать другой отдельный заказ. Независимые браузеры с разными ключами — разные
заявки. Номер не даёт публичного доступа к персональным данным.

## Безопасные локальные проверки

Без установки зависимостей:
- node --test tests/orders-client.cjs
- node scripts/build-order-catalog.cjs
- node tests/orders-browser.cjs
- node scripts/check-stage1.cjs

Браузерный тест использует уже установленный Playwright/Chrome, сервер только
127.0.0.1 и подставные ответы PHP. Все внешние запросы блокируются.
При другой установке задаются ZT_PLAYWRIGHT_MODULE и ZT_CHROME_PATH.
Настоящий PHP/MySQL этим тестом не проверяется.

Подготовленные, но не выполненные здесь проверки:
- php -l для каждого PHP-файла.
- php tests/orders-validation.php — без сети и базы.
- php tests/orders-mysql.php — только одноразовая пустая ЛОКАЛЬНАЯ MySQL 8.

MySQL-тест требует явный ZT_ALLOW_DISPOSABLE_TEST_DB=yes и DSN строго вида
mysql:host=127.0.0.1;port=3306;dbname=zt_test_orders_EXAMPLE;charset=utf8mb4
(имя после префикса — только маленькие латинские буквы, цифры и подчёркивания).
Ещё нужны ZT_TEST_MYSQL_USER и ZT_TEST_MYSQL_PASSWORD. Он откажется работать с
непустой схемой, не читает рабочую конфигурацию и не принимает удалённый адрес.
Тест создаёт таблицы и искусственную ошибку очереди ТОЛЬКО в одноразовой базе.
Оставляет тестовые таблицы для осмотра, ничего не удаляет из рабочей базы.
Не запускать против туннеля/проброса к рабочей БД.

## Необходимые действия в REG.RU — только после отдельного разрешения

1. Сначала подтвердить безопасную область публикации workflow. Не переносить
   ветку в main при старом workflow: он публикует почти всё содержимое!
2. До публикации проверить PHP 8.3 и pdo_mysql, MySQL 8 и результаты PHP-тестов
   в изолированном локальном окружении. Нужны также проверка параллельных повторов
   и реального HTTP до полноценного приёма.
3. Снять резервные копии кода и базы, проверить отсутствие таблиц zt_orders,
   zt_order_items, zt_notification_queue, zt_order_rate_limits.
4. Просмотреть SQL. По отдельному разрешению применить 001-orders.sql к нужной
   базе вручную, без автоматического выполнения приложением. DDL MySQL не
   откатывается общей транзакцией: если создание остановилось, сначала осмотр.
5. Создать ограниченного пользователя приложения: SELECT/INSERT для заказов,
   позиций и очереди, SELECT/INSERT/UPDATE для счётчиков. Без DROP/ALTER/GRANT.
   Пользователь миграции должен быть отдельным.
6. ВНЕ публичной папки создать закрытую папку заказов. В неё положить lib/,
   catalog.json, consent.html и config.php на основе примера. migrations/ и
   тесты публиковать не нужно. Установить права только для нужного пользователя.
7. Заполнить локально DSN, пользователя, пароль, случайный rate_secret (64 hex),
   точный HTTPS origin. Реальные значения не добавлять в GitHub/чат.
8. В FastCGI настроить ZT_ORDERS_PRIVATE_DIR абсолютным путём к закрытой папке.
   Возможность настройки нужно подтвердить у хостинга. Если переменная недоступна,
   отдельным согласованным изменением можно указать только абсолютный путь
   в шлюзе PHP, без паролей. До этого шлюз отвечает 503.
9. В публичную папку вручную положить только api/v1/orders.php. Конфигурация
   enabled=false: приём остаётся выключенным.
10. Актуализировать и согласовать документы: текущий legal.html всё ещё описывает
    демонстрацию и прямо говорит, что формы не сохраняют данные. Мы его не
    переписывали. Определить фактические сроки хранения, доступ и работу с заказами.
    После утверждения синхронно обновить версию согласия, документ и закрытый снимок.
11. Согласовать ручной просмотр заявок до этапа уведомлений. Нужна процедура
    регулярной проверки новых заказов в закрытом интерфейсе базы, без публичного
    экспорта и без открытия phpMyAdmin посторонним.
12. После разрешения опубликовать проверенную витрину, проверить API на специально
    согласованных тестовых данных и только затем включить enabled=true.
    Проверить сохранённые позиции и ровно одно pending-уведомление.
13. До включения проверить HTTPS, закрытый каталог, лимиты тела запроса,
    отсутствие вывода ошибок PHP и запрет публичных дампов/логов/резервных копий.

Cron в этом этапе не нужен. Счётчики имеют expires_at, но автоочистка ещё не
подключена: до длительной эксплуатации согласовать регламент очистки только
просроченных счётчиков. Обычные заказы и ключи повторов при ней не удалять.
Лимит приложения не заменяет ограничения нагрузки на стороне хостинга.
Сырые IP не сохраняются; используются HMAC и окно 10 минут. Прокси-заголовки
не считаются доверенными: проверить реальное REMOTE_ADDR на хостинге.

## Безопасная публикация и откат

Порядок: разрешение на workflow -> его отдельная проверка -> резервные копии ->
изолированные PHP/MySQL тесты -> разрешение на рабочую миграцию -> выключенный
серверный код -> витрина -> проверка -> разрешение включить приём.

FTPS не атомарен. Нужен контролируемый промежуток публикации; прежние и новые
файлы JS не должны смешиваться. Обновлены версии изменённых скриптов в index.html.
PHP и закрытые файлы не входят в предложенный автоматический деплой.

При откате сначала enabled=false: новые заявки честно отклоняются.
Не восстанавливать старую базу целиком поверх новых заказов.
Никакой down-миграции с DROP нет. Четыре таблицы и новые данные остаются.
При возврате прежнего оформления сохранить безопасные app.js, details.js,
checkout-client.js и checkout.js этого этапа, а приём выключить enabled=false.
Не возвращать старый completeCartOrder(), очищающий корзину без сервера,
или ложную надпись «заявка отправлена».
Записи очереди остаются pending до отдельно согласованного следующего этапа.
