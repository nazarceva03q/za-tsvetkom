# Уведомление владелице в личные VK — только проект

Рекомендуемый простой вариант: отдельный закрытый PHP-отправщик на REG.RU,
запускаемый cron. Он читает существующую очередь и вызывает messages.send от
сообщества на один заранее разрешённый VK ID владелицы. Yandex Cloud и код
административного бота для этого не нужны. Входящие сообщения не обрабатываются.

Ничего из этого пока не включено. Существующий бот не изменялся.

## Согласованный состав сообщения

Новый заказ № [номер]
Создан: [дата и время сохранения, с указанием часового пояса магазина]
[Название товара] × [количество] — [сумма позиции]
Итого по товарам: [сумма заказа] ₽
Доставка: согласуется отдельно.

В уведомление НЕ включать имя, телефон, адрес, комментарий, пожелания, выбранный
канал связи и персонализацию покупателя. Товарные названия брать из снимка заказа,
без дополнительных заметок покупателя. Не подставлять минимальную цену оформления
«Для бизнеса» как окончательную цену покупки. Для обращения без позиций нужна
отдельная подпись «Обращение», а не выдуманный список товаров.

Сумма первого этапа — сумма товаров, не окончательная стоимость с доставкой.
Уточнение необходимо сохранить в тексте. Форматировать деньги из целых копеек.
Дата в базе UTC; при показе явно указать часовой пояс магазина (Пермь).

## Надёжная отправка

1. Заказ уже записан вместе с одной pending-записью. Подтверждение покупателю
   не ждёт VK и не отменяется из-за его недоступности.
2. Cron берёт небольшую порцию задач. Короткая транзакция отмечает задачу занятой
   и устанавливает срок блокировки. Сетевой запрос не держит SQL-транзакцию.
3. До первого запроса закрепить получателя и постоянный vk_random_id за задачей.
   Для этого понадобится отдельная согласованная доработка очереди, сейчас её нет.
4. Вызывать messages.send с одним peer_id владелицы и тем же random_id на повторе.
   Проверять JSON и поле error, а не только HTTP 200.
5. При подтверждении помечать sent. При временной ошибке — следующая попытка
   с возрастающей задержкой; при запрете сообщений/неверном токене — видимая
   ошибка оператору без бесконечных немедленных повторов.
6. Просроченную блокировку разрешать забирать другому запуску.
7. Хранить код ошибки без тела сообщения/токена/контактов. Неполадка VK
   не должна удалять заказ или ожидание уведомления.
8. Сохранять одну задачу на заказ/тип/получателя. Учитывать сбой после принятия
   сообщения VK, но до записи sent: постоянный random_id уменьшает риск дубля,
   абсолютное «ровно один раз» при любой сетевой ошибке обещать нельзя.
9. Контроль зависшей очереди показывать владелице в защищённом интерфейсе.

Интервал cron — минимальный доступный на тарифе, после реальной проверки
(например, каждую минуту, если это разрешено). Не обещать мгновенную доставку.
Команда запускает PHP CLI-файл вне публичной папки, не URL с секретом.
Токен сообщества и ID владелицы — в закрытой конфигурации, не в GitHub.

Официальная схема VK: https://github.com/VKCOM/vk-api-schema/blob/master/messages/methods.json
(messages.send: group token, peer_id, random_id; разрешение на сообщения
сообщества необходимо проверить для конкретной владелицы).

## Полные сведения — только через защищённый интерфейс

Следующим отдельно согласованным изменением подготовить минимальный экран только
для чтения: список новых заявок, номер, позиции, контактные данные и получение.
Доступ по HTTPS, отдельная учётная запись владелицы, стойкий хеш пароля,
ограничение попыток и безопасная сессия; никакого доступа только по номеру заказа.
Формировать страницу с экранированием текста и подготовленными запросами,
Cache-Control: no-store. Пароль/ключ не помещать в ссылку из VK.

До готовности такого экрана не обещать его наличие. Временный просмотр возможен
через закрытую панель базы REG.RU с доступом только владелице, но это не удобный
постоянный интерфейс магазина. Перед реальным запуском решить, достаточно ли
временного способа или сначала нужна отдельная реализация экрана.

Установка sender, изменение схемы, cron, выдача токена и тест отправки требуют
следующего отдельного разрешения. Сейчас подготовлено только решение.

Важно: новый отправщик не вмешивается в переписку покупателей. Но в существующем
боте уже есть покупательские сценарии; эта схема сама по себе их не отключает.
Перед подключением кнопки обычной переписки отдельно согласовать их ограничение,
не меняя бот на этом этапе.

Исключение контактов уменьшает объём передачи, но номер заказа и его состав
не следует автоматически считать необратимо обезличенными. Перед подключением
нужно согласовать основание передачи, получателя, сроки сообщений и отразить
фактическую обработку в политике. Никаких сообщений сейчас не отправлено.
